# 渲染性能：实测瓶颈与开关

本文件记录一次实测优化，不是泛泛的“性能建议”。数值来自本机（Apple Silicon、16 逻辑核、540×960 草稿），不同机器会变，但相对关系可参考。

## 结论

| 场景 | 优化前 | 优化后 |
| --- | --- | --- |
| 19.4 秒片子，分镜全部命中缓存 | 13.4s | **1.4s** |
| 19.4 秒片子，分镜需重绘（并发2） | 16.8s | **6.7s**（并发8） |
| 7 分 17 秒整片 | 约 30 分钟量级 | 见下方实测 |

三处改动：

1. **静音时间轴不再整片渲染音轨。** 旧实现无论有没有配音，都会把整条时间轴以 `codec:'wav'` 再渲染一遍来合成连续音轨。静音片没有音源，等于白跑一整趟：19.4 秒片子中占 11.7s，7 分钟片子中占数分钟。现在 `needsAudioTrack()` 检测到没有音源时，直接用 FFmpeg 生成等长静音轨。
2. **并发从写死 2 改为自动。** 取 `min(8, CPU-1)`，可用 `SHENYING_CONCURRENCY` 覆盖。帧由并行 Chromium 标签页渲染，这一项在实测中接近线性收益。
3. **缓存指纹不再包含 `server/`。** 原先改渲染编排也会让所有分镜缓存失效；现在只对 `src/`、`shared/`、`package-lock.json` 求指纹，因为只有它们影响像素。纯编排改动不再清空缓存。

另外草稿改用 `x264Preset: veryfast`、正式用 `medium`。实测短片里编码不是瓶颈（6.6s vs 6.7s），它只在长片上略微减少尾部时间，不要指望它带来量级变化。

## GPU / 硬件编码：实测没有收益

- Remotion 的帧来自 headless Chromium 截图，**合成与光栅化主要在 CPU**；最终编码是 libx264，也是 CPU。
- 我们试了 Chromium 的 `GL=angle`（macOS 上走 Metal）：同一镜头 **14.2s**，比默认 **6.7s** 慢一倍。原因是这类画面主要是 SVG、CSS 滤镜与文字，软件光栅已经够快，ANGLE 反而增加初始化与拷贝开销。
- 因此默认不启用 GPU 后端。需要试验时用 `SHENYING_GL=angle`（可选 `egl`/`vulkan`/`swiftshader`），但请先自测；不要假定“开了 GPU 就一定快”。
- 目前没有接入 NVENC / VideoToolbox 硬件编码；`codec:'h264'` 走 libx264。

## 如果还要更快

按收益排序，尚未实现：

1. **减少重滤镜。** 玻璃卡的 `feDropShadow` 与 `blur` 是每对象每帧开销，长时间轴草稿可考虑降级为纯描边。
2. **只重绘变化分镜**（已有分镜级缓存），把改稿范围控制在一两幕，而不是整片重跑。
3. **缩短静音估算时长。** 估算按每秒 4 字，比真实语速慢，片子会被拉长，渲染帧数随之增加。真实 TTS 时间轴通常更短。
4. **降低草稿分辨率**（当前 0.5 倍，竖屏 540×960）。清晰度与速度需要业务取舍。

## master与配音

上面的分镜缓存只适用于scenes。master单根画布整片一次渲染，无分幕缓存；没有配音时以本地PCM混合未静音合成音效，有配音时额外渲染整条配音/音效轨。sfxMuted默认true，不能把静音触发点当作可听音源。帧数固定，配音超段长报错，不因配音改变运动时长。

## 边界

- 这些都是编排层的加速，**不改变画面内容**。改动后需重新渲染确认输出，并做人工验收。
- 清理 `out/scene-cache` 会丢失加速收益，属可重建数据；不要在没有确认任务停止时清理。
- 并发不是越高越好：超过物理核数后收益递减，且内存占用上升；可用 `SHENYING_CONCURRENCY` 回退到 2 复现旧行为。
